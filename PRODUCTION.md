# Запуск «Первика» на собственном сервере

Конфигурация рассчитана на один экземпляр приложения, PostgreSQL и HTTPS через Caddy. Начальная конфигурация: 2 ядра приложению, 1 ГБ памяти приложению, 1 ГБ базе; для всей системы разумно выделить минимум 4 ГБ RAM и SSD. Это исходная конфигурация, её реальную ёмкость нужно измерить на выбранном сервере.

## Подготовка

1. Установить Docker Engine и Compose plugin. Перенести исходники без `node_modules`, `.env*`, `.aistudio` и тестовых баз. Не публиковать порт PostgreSQL.
2. Скопировать `docker/production.env.example` в `.env.production.local`. Заполнить домен, почту для сертификата, случайный шестнадцатеричный пароль PostgreSQL и реквизиты администратора. Хэши создаёт существующая команда `npm run setup:admin`. Значения передаются через файл, не через историю команд.
3. **Для переноса существующих данных сохранить прежний `AUTH_SESSION_SECRET` без изменений.** Он нужен для расшифровки базы и не восстанавливается из пароля администратора. Хранить отдельную защищённую копию ключа вне резервных копий базы. Смена ключа без миграции делает данные нечитаемыми.
4. Направить DNS домена на сервер. Открыть TCP 80/443 и при необходимости UDP 443. Других публичных портов конфигурация не открывает. У сервера должен быть выход в интернет для сертификатов.

Проверить конфигурацию без вывода её секретных значений:

```sh
docker compose --env-file .env.production.local -f compose.production.yaml config --quiet
```

## Перенос базы

На текущем компьютере создать свежую копию: `npm run db:backup`. Перед окончательным переносом закрыть приём изменений режимом техработ, дождаться завершения действий и сделать финальную копию. Переносить `.dump` защищённым каналом. Учётные записи, заявки, профили, рейтинг, календарь и фотографии находятся в PostgreSQL.

На новом сервере сначала запустить только базу:

```sh
docker compose --env-file .env.production.local -f compose.production.yaml up -d --wait database
```

Для **пустой новой базы**, пока приложение остановлено, восстановить подготовленную копию:

```sh
docker compose --env-file .env.production.local -f compose.production.yaml exec -T database pg_restore -U pervik -d pervik --clean --if-exists --no-owner --exit-on-error < /protected/path/platform.dump
```

Команда восстановления заменяет таблицы целевой базы. Не выполнять её на работающей платформе и не направлять в чужую базу. Резервная копия перед восстановлением обязательна, если в целевой базе уже есть данные. Для нового пустого проекта шаг восстановления пропустить.

Запустить платформу:

```sh
docker compose --env-file .env.production.local -f compose.production.yaml up -d --build --wait
docker compose --env-file .env.production.local -f compose.production.yaml ps
```

При старте старая зашифрованная запись переносится в отдельные зашифрованные записи PostgreSQL. Миграция транзакционная; исходный снимок остаётся как `private-state-legacy-v1`. Старый образ после миграции не совместим с новой схемой. Для полного отката потребуются предыдущий образ **и** копия базы до миграции, а не только откат контейнера.

## Проверка перед открытием

- `/healthz` — процесс работает; `/readyz` — база доступна и читается. Режим техработ не отключает эти проверки и доступ администратора.
- Войти администратором, проверить количество сотрудников и заявок, профиль, фотографии, календарь, рейтинг, выдачу доступов. Открыть сайт для участников после проверки.
- Контейнер `backup` сразу делает копию и затем повторяет её каждые 24 часа. Хранение 14 дней в `data/backups/production`; ошибки повторяются через 5 минут. Проверять `last-success`, настроить внешнее уведомление об отсутствии свежей копии. Файлы содержат персональные данные; каталог закрыт правами 0700/0600.
- Копировать резервные файлы в отдельное защищённое хранилище. Копии на диске сервера не защищают от потери этого диска. **Ключ шифрования хранить отдельно.** Раз в месяц проверять восстановление на отдельной базе.
- Поставить внешний монитор HTTPS и `/readyz`. В логах приложения раз в минуту есть число запросов, ответов 5xx, медленных ответов и использование памяти; тела запросов и контакты не записываются. Логи Docker ограничены 3 файлами по 10 МБ.

## Нагрузка и масштабирование

Пул PostgreSQL ограничен 8 соединениями, очередь — 128; запросы и блокировки имеют тайм-ауты. Одновременно обслуживается до 128 API-запросов, до 4 загрузок фотографий. Вход: 12 попыток в минуту на сочетание IP и логина, до 120 входов в минуту на IP; записи: 180 в минуту, для администратора 360; чтение: 12 000 в минуту. При перегрузке выдаются 429/503 с `Retry-After`, данные не записываются частично. Большая школьная сеть с одним внешним IP может потребовать согласованной настройки лимитов.

Клиент применяет ETag, не сохраняет API-данные в service worker/localStorage, хранит ограниченный кеш только в памяти и сбрасывает его при изменениях/выходе. Неизменившиеся данные возвращаются как 304. При ошибках связь восстанавливается с увеличением интервала до минуты. Права и режим техработ проверяются до ответа 304.

Текущая схема держит расшифрованный снимок в памяти процесса и сериализует записи через одну транзакционную блокировку. Это обеспечивает согласованность; **бесконечную нагрузку не обещает**. Перед многократным ростом нужна пагинация больших списков, выборочные SQL-запросы и общий ограничитель запросов для нескольких экземпляров. Не увеличивать число реплик без общего rate limiter и повторного нагрузочного испытания. При установке внешнего CDN/proxy отдельно настроить доверенные IP; произвольные `X-Forwarded-For` нельзя принимать от интернета.

Нагрузочные результаты текущего компьютера и точные границы проверки: `deliverables/production-readiness/REPORT.md`. Скрипты работают только с базами `pervik_audit_*` и портами 3101/3102. Нагрузочный тест на рабочем сервере выполняется в согласованное окно на отдельной базе; прежний результат не является гарантией для другого оборудования.
