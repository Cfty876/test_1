# Проверка готовности «Первика» — 1 ноября 2026

## Итог и границы

Исправлены основные узкие места хранения, чтения, обработки паролей и HTTP-запросов. Подготовлена отдельная конфигурация собственного сервера с PostgreSQL, HTTPS и ежедневными резервными копиями. Рабочие записи не использовались в нагрузочных тестах: все изменения и проверки отказов выполнялись на отдельных `pervik_audit_*` базах и портах 3101/3102.

Это проверка конкретной версии на конкретном компьютере, а не гарантия бесконечного количества посетителей. Выход в публичную эксплуатацию требует реального сервера/домена, переноса данных и повторного замера на выбранном оборудовании. Vercel не обновлялся: ранее выбран бесплатный локальный режим, облачное Blob-хранилище остаётся заблокированным лимитами.

## Найдено и исправлено

| Риск | Исправление |
|---|---|
| Каждый запрос расшифровывал весь JSON базы, каждое действие переписывалo его целиком | Отдельные AES-GCM записи PostgreSQL, непрозрачные HMAC-ключи, запись только изменённых объектов, кеш неизменяемого снимка по ревизии |
| Потеря согласованности при конкурирующих действиях | Общая транзакционная блокировка сохраняет инварианты разных коллекций; версии, квоты и полномочия проверяются внутри транзакции |
| Повторные загрузки всех данных каждые 5 секунд | ETag/304 после проверки доступа, объединение параллельных чтений базы, кеш проекций, gzip, ограниченный кеш в памяти клиента |
| Вложенные линейные поиски в больших списках | Индексы Map для сотрудников, изображений, проектов и профилей |
| Синхронный scrypt блокировал обработку запросов | Асинхронный scrypt, максимум 2 одновременные операции и 24 ожидающие; вычисление вне транзакций |
| Два одинаковых запроса выдачи доступа могли конфликтовать | Стабильная уникальная соль для одного билета и проверка существующих реквизитов; повтор после сброса пароля не возвращает старый пароль |
| Нет ограничений очередей и попыток входа | Ограничения API, загрузок, пула БД, тела/времени запроса и попыток входа; 429/503 с Retry-After |
| При выходе из кабинета могли оставаться кешированные личные ответы | Кеш только в памяти, ограничен 16 МБ/16 ответами, сбрасывается при изменениях и смене сеанса; API не сохраняется service worker |
| Фото проверялось только по сигнатуре | Проверка размеров JPEG/PNG/WebP без декомпрессии, лимит 20 Мп/8192 px, 3 МБ, максимум 4 параллельные загрузки |
| Остановка процесса могла обрывать работу и не закрывать пул | Graceful shutdown до 25 секунд, завершение соединений БД; отдельные liveness/readiness проверки |
| Потеря БД не была оперативно видна мониторингу | Readiness и метаданные имеют дедлайн 3 секунды; 503 при потере БД, восстановление связи без перезапуска |
| Скрипт ежедневной копии не запускался с CRLF | Исправлен LF, закреплён `.gitattributes`, реальный запуск копирования в Linux проверен |
| Известные уязвимости зависимостей | Обновлён body-parser, безопасный совместимый override Zod без отката Blob; удалён неиспользуемый Gemini SDK и build tools из runtime |
| Нет завершённой конфигурации своего сервера | `compose.production.yaml`, Caddy HTTPS, закрытая сеть БД, read-only приложение без capabilities, лимиты ресурсов и логов, резервные копии |

Миграция хранит исходную зашифрованную запись как `private-state-legacy-v1`. Контрольные суммы всех коллекций, количество и порядок записей до и после миграции совпали. Старое приложение после миграции намеренно не может писать в старый снимок.

## Нагрузочные измерения

Docker Desktop, Windows, компьютер с 8 ГБ RAM; приложение ограничено 2 CPU / 1 ГБ. PostgreSQL 17. Основной синтетический набор: 1000 сотрудников, 3000 заявок, 1000 реализаций, 1000 участников базы, 5000 записей баллов. Функциональные проверки добавили небольшое число тестовых записей. Данные — вымышленные, адреса `example.invalid`.

Полные ответы, 20 одновременных клиентов, по 8 секунд на маршрут. Начальная проверка готовности отделена от замера. В приведённых завершённых замерах нет ответов 5xx и сетевых ошибок.

| Маршрут | Было: p95 / запросов в секунду | Стало: p95 / запросов в секунду |
|---|---:|---:|
| Главная | 7308 мс / 3,5 | 148 мс / 199,9 |
| Состояние сайта | 1700 мс / 13,6 | 19 мс / 1630,9 |
| Кабинет администратора | 3427 мс / 7,0 | 342 мс / 71,8 |
| Рейтинг и календарь | 1984 мс / 10,6 | 158 мс / 165,2 |

Источник: `baseline-20.json`, `final-full-20.json`. Исходный сервер не сжимал API, новая версия использует gzip; улучшение относится ко всему набору исправлений. Нельзя выдавать измерения чтения за производительность записи.

Дополнительно: `final-conditional-100.json` — 100 параллельных клиентов с условными запросами; `mixed-100.json` — 100 разных председателей, пять видов чтения, параллельная подача новых заявок. Итоговый смешанный прогон: 4017 чтений за 20.8 с, 192.9 запроса/с, p95 1165 мс, p99 1297 мс; 18 заявок успешно записаны. Ошибок 5xx и сетевых ошибок нет. Точные результаты и статусы находятся в этих JSON. Смешанный тест важнее чистого 304-теста для оценки реальной работы. Пиковый бесконечный цикл запросов не равен количеству людей, заходящих на сайт за день.

## Функциональные и конкурентные проверки

- Локальное хранилище и HTTP-защита: 19 проверок с учётом родительского сценария; PostgreSQL: 14; отдельный SQL store: 5. Ошибок в итоговых прогонах нет.
- Вход с обязательным ознакомлением с политикой, неверные/слишком длинные пароли, выдача доступов, параллельный повтор выдачи, смена пароля и отзыв прежнего сеанса.
- Подача инициативы, валидация контактов, защита от дублей, личный код без выдачи контактов, решение куратора, доработка и отзыв, обложка и подборка, браузерные лайки.
- Профиль, контакты, видимость сотрудникам, конфликт версии; запрет просмотра школьному участнику чужих профилей.
- Взятие проекта с датами, одобрение городским председателем, общий календарь, квоты команды. Две одновременные попытки занять последнее место дают одно одобрение и один конфликт.
- Загрузка/просмотр приватной фотографии, отчёт со ссылками и подтверждение другим уполномоченным сотрудником.
- Баллы: корректность доказательств, отсутствие повторной заявки, два одновременных решения дают одно начисление, повторная отмена блокируется, рейтинг возвращается к прежней сумме.
- Календарь: права, корректность дат, повтор отправки и конфликт редактирования.
- Техработы: доступ только администратору, запрет чтения/записи участникам, работа входа и восстановления администратором, конфликт версии переключателя.
- 50 параллельных транзакций без потерянных записей; порядок при 20 перестановках/вставках; rollback; запрет одинаковых ключей; обновление кеша после записи из второго Node-процесса.
- Запрет чужого Origin, неверного JSON, больших тел, поддельного X-Forwarded-For при ограничении входов, фото с недопустимыми размерами.

`tsc --noEmit`, production build, npm audit — проходят; audit: 0 известных уязвимостей на дату проверки. Docker production-конфигурация и Caddyfile прошли валидацию. HTTP проверка: `/healthz` 200, `/readyz` 200, неизвестная страница 404, неизвестный API 404.

## Восстановление и отказ базы

Копия тестовой базы восстановлена `pg_restore --exit-on-error` в отдельную базу. Совпали SHA256 полного состояния, порядок/число записей и количество приватных файлов: `restore.json`. Linux-контейнер ежедневного копирования действительно создал `.dump` и `last-success`; ожидание 24 часов и авария физического диска не имитировались.

Для проверки отказа отключалась сеть только тестового приложения, рабочая БД продолжала работать. `/healthz` остался 200, `/readyz` и публичный API вернули 503 примерно за 3 секунды. После подключения сети чтение восстановилось без перезапуска. Рабочий сайт для этой проверки не отключался.

## Что ещё требуется именно на сервере

1. Домен, TLS, реальные секреты и перенос базы по `PRODUCTION.md`. Подписи документов/содержимое политики не являются предметом этого технического испытания.
2. Внешний монитор `/readyz`, уведомления о старых копиях и защищённая копия данных вне диска сервера. Ключ шифрования — отдельно.
3. Повторная нагрузочная проверка на реальном сервере и канале, длительный прогон, согласованная целевая аудитория и запас ресурсов.
4. Визуальный/browser end-to-end контроль остаётся отдельно: доступный Computer Use в этой сессии не запускался из-за ошибки среды. Проверки HTTP/API/БД не подменяют осмотр мобильного браузера.

Текущий store остаётся снимком в памяти с общей блокировкой записей. При кратном росте данных нужны пагинация и выборочные SQL-запросы; для нескольких экземпляров — общий rate limiter. Эти ограничения не скрываются за результатами короткого теста.
